A strong training score does not prove that a model is useful. Choose an evaluation that matches the task, measure the costs of errors, and plan how to monitor the model after deployment.

## Choose an evaluation metric

The first example has high accuracy but fails to detect the examples we care about:

```python run setup title="a 99% accurate model that is worthless"
import numpy as np, matplotlib.pyplot as plt

n = 10_000
truth = np.zeros(n, dtype=int)
truth[:100] = 1                      # 1% fraud
rng = np.random.default_rng(0)
rng.shuffle(truth)

always_no = np.zeros(n, dtype=int)
print(f"model that always says 'not fraud': accuracy {(always_no == truth).mean():.2%}")
print(f"frauds caught: {((always_no == 1) & (truth == 1)).sum()} of {truth.sum()}")
```

Accuracy can hide poor performance on a rare class. Inspect the confusion matrix to see what the model gets right and wrong:

```python run title="the confusion matrix, which is the real object"
scores = np.where(truth == 1,
                  rng.normal(0.65, 0.20, n),
                  rng.normal(0.30, 0.18, n)).clip(0, 1)

def confusion(y, pred):
    tp = int(((pred == 1) & (y == 1)).sum()); fp = int(((pred == 1) & (y == 0)).sum())
    fn = int(((pred == 0) & (y == 1)).sum()); tn = int(((pred == 0) & (y == 0)).sum())
    return tp, fp, fn, tn

tp, fp, fn, tn = confusion(truth, (scores > 0.5).astype(int))
print(f"                  predicted fraud   predicted ok")
print(f"actually fraud  {tp:14,d} {fn:14,d}")
print(f"actually ok     {fp:14,d} {tn:14,d}")
print(f"\nprecision {tp/(tp+fp):.3f}  — of those flagged, how many really were fraud")
print(f"recall    {tp/(tp+fn):.3f}  — of the real frauds, how many did we catch")
```

The confusion matrix separates true positives, false positives, true negatives, and false negatives. Two useful summaries are:

- **Precision:** among the cases predicted positive, how many are positive?
- **Recall:** among the positive cases, how many did the model find?

Precision and recall usually trade off. Predicting every example as positive gives perfect recall but may have poor precision. Predicting only the most certain case can give high precision but miss many positives.

## Choose a decision threshold

A classifier may return a probability or score. The threshold converts that score into a decision.

```python run title="one model, many operating points"
rows = []
for t in [0.2, 0.35, 0.5, 0.65, 0.8]:
    tp, fp, fn, tn = confusion(truth, (scores > t).astype(int))
    prec = tp / max(tp + fp, 1); rec = tp / max(tp + fn, 1)
    rows.append((t, tp, fp, fn, prec, rec))
    print(f"threshold {t:.2f}   caught {tp:3d}  false alarms {fp:4d}  missed {fn:3d}   "
          f"precision {prec:.2f}  recall {rec:.2f}")
```

Changing the threshold changes precision and recall without retraining the model. Choose a threshold based on the cost of the different errors.

```python run title="pick it with money, not with intuition"
COST_FALSE_ALARM = 4        # an analyst spends five minutes
COST_MISSED_FRAUD = 500     # you eat the chargeback

best = None
for t in np.linspace(0.05, 0.95, 91):
    tp, fp, fn, tn = confusion(truth, (scores > t).astype(int))
    cost = fp * COST_FALSE_ALARM + fn * COST_MISSED_FRAUD
    if best is None or cost < best[1]:
        best = (t, cost, fp, fn)

print(f"cost-optimal threshold {best[0]:.2f}  ->  total cost {best[1]:,}")
print(f"  {best[2]} false alarms, {best[3]} missed frauds")
d = confusion(truth, (scores > 0.5).astype(int))
print(f"default 0.50 threshold  ->  total cost "
      f"{d[1] * COST_FALSE_ALARM + d[2] * COST_MISSED_FRAUD:,}")
```

The best threshold depends on the task. Write down the cost of a false positive and a false negative, then compare the resulting trade-offs with the people responsible for the decision.

The next plot shows performance across thresholds:

```python run title="the whole curve"
ths = np.linspace(0.01, 0.99, 200)
prec, rec = [], []
for t in ths:
    tp, fp, fn, tn = confusion(truth, (scores > t).astype(int))
    prec.append(tp / max(tp + fp, 1)); rec.append(tp / max(tp + fn, 1))

plt.figure(figsize=(5, 3.2))
plt.plot(rec, prec)
plt.axhline(truth.mean(), ls=":", c="grey")
plt.text(0.55, truth.mean() + 0.02, "random guessing", fontsize=8, color="grey")
plt.xlabel("recall"); plt.ylabel("precision"); plt.title("precision–recall curve")
plt.tight_layout()
```

A precision-recall curve is often useful when positive examples are rare. A receiver operating characteristic curve shows the trade-off between true-positive rate and false-positive rate. Neither curve replaces checking the actual operating point, baseline, and costs.

## Check calibration

A model is calibrated when examples assigned probability p are positive about p of the time. For example, among cases assigned probability 0.7, about 70% should be positive.

```python run title="a confident model is not a correct one"
def calibration(probs, y, bins=8):
    edges = np.linspace(0, 1, bins + 1)
    out = []
    for lo, hi in zip(edges, edges[1:]):
        m = (probs >= lo) & (probs < hi)
        if m.sum() > 20:
            out.append((probs[m].mean(), y[m].mean(), int(m.sum())))
    return np.array(out)

cal = calibration(scores, truth)
plt.figure(figsize=(4.4, 3.4))
plt.plot([0, 1], [0, 1], "k:", label="perfectly calibrated")
plt.plot(cal[:, 0], cal[:, 1], "o-", label="this model")
plt.xlabel("predicted probability"); plt.ylabel("observed frequency")
plt.legend(); plt.tight_layout()
print("when it says 0.7, does it happen 70% of the time?")
```

Ranking and calibration are different. A model can rank examples correctly while its probabilities are too high or too low. Calibration matters when probabilities are used to estimate risk, cost, or expected value. Reliability plots and methods such as temperature scaling can help; fit any calibration method on data separate from the final test set.

## Monitor the model after deployment

Performance can change when the world or the data collection process changes. This is called distribution shift. Monitor input data and, when labels become available, monitor outcomes too.

Model predictions can also change the data you later collect. A fraud model that blocks transactions may never learn whether blocked transactions were fraudulent. Consider how the system's actions affect future feedback.

Training-serving skew happens when features are computed differently during training and deployment. Use shared feature code where possible, and log the model version alongside each prediction so results can be traced later.

Deployment also needs ordinary software practices: version the model, pin dependencies, log useful inputs and outputs, monitor service health, and keep a way to roll back.

## Read a research paper

You can read many papers in passes:

1. **First pass:** read the title, abstract, figures, and conclusion. Identify the problem and the main result.
2. **Second pass:** read the method and experiment sections. Ask what the inputs and outputs are, which loss is used, what model is compared, and whether the evaluation is fair.
3. **Reproduce a result:** when the paper matters to your work, run an experiment or implement a small version.

Check the baseline carefully. Was it tuned fairly? Was the test set kept separate? Were results averaged over several runs? These questions help you judge a result even before you understand every equation.

Here are common symbols you will see:

| Symbol | Meaning |
|---|---|
| θ | the model parameters |
| L(θ) | the loss as a function of the parameters |
| ∇θ | gradient with respect to the parameters |
| Eₓ~D[·] | average over data drawn from distribution D |
| argmaxθ | the parameter value that maximizes an expression |
| pθ(y | x) | model probability for y given x |
| ŷ and y | prediction and target |
| ‖·‖₂ and ‖·‖₁ | Euclidean and absolute-value norms |
| ⊙ | elementwise multiplication |

For example, minimizing average prediction loss plus a penalty on large parameters combines two ideas from this course: fit the data and regularize the model.

## A checklist for a first project

1. Define the feedback, task, features, and target.
2. Choose a validation split that resembles deployment.
3. Calculate a simple baseline.
4. Estimate the costs of false positives and false negatives.
5. Fit a simple model and compare its results.
6. Inspect the examples it gets wrong.
7. Check for leakage and choose a decision threshold.
8. Decide how to monitor performance after deployment.

Before choosing a model, define the task. What should the system predict or decide? What examples will it use? How will you tell whether its predictions help?

Clear answers guide your choice of training data, task, model, and evaluation. They can also show that a simple rule or better data collection would solve the problem.

## Three questions to ask before modeling

Every machine-learning project has answers to three separate questions:

| Question | Examples of answers |
|---|---|
| What feedback is available? | labels, patterns in unlabelled data, rewards |
| What should the model produce? | a class, number, ranking, sequence, or groups |
| What model family will produce it? | linear model, tree, neural network |

A phrase such as “supervised classification with a gradient-boosted tree” gives one answer to each question. Keeping the questions separate helps you compare approaches.

The feedback choice affects what data you need. Collecting labels can take time and money. The model family is easier to change later, so first check what information you can collect and use.

## Question 1: what feedback do you get?

In **supervised learning**, each training example comes with a target answer. For example, an email might be labelled “spam” or “not spam.” The model learns to predict that target from the other information in the example.

Labels can be expensive to create. A radiologist who labels scans has less time for other work. Common options include asking experts, paying annotators, using crowdsourcing, or finding labels in records that already exist. Check how each source defines the label and whether those labels match the decision you want the model to support.

In **self-supervised learning**, the training target is derived from the data itself. A common language-model task is to hide or shift part of a sentence and train the model to predict the next token.

```python run title="self-supervision, in four lines"
text = "the quick brown fox jumps over the lazy dog"
tokens = text.split()
pairs = [(tokens[:i], tokens[i]) for i in range(1, len(tokens))]
for context, target in pairs[:4]:
    print(f"{' '.join(context):32s} -> {target}")
```

This example creates several training pairs from one sentence. Large text collections provide many such examples without a person labelling every next word. The model still needs carefully chosen data, a training objective, and evaluation. Predicting the next token is one common objective; it is not the whole of language-model training.

In **unsupervised learning**, examples have no target labels. A model may group similar records, compress them into fewer dimensions, or flag unusual examples. Since there is no known answer, a numerical score may not tell you whether the result is useful. You need a way for a person or a downstream task to judge it.

In **reinforcement learning**, an agent takes actions and receives rewards. The reward may come later, and it does not necessarily identify the correct action at each step. The agent's actions also affect what it sees next. This setup is used in areas such as game-playing and robotics. Some language-model systems also use reinforcement-learning methods during post-training. The [optional guide](/extras/reinforcement-learning/) introduces the main terms.

## Question 2: what should the model produce?

The output determines which loss and evaluation measures make sense. A loss helps fit the model; a metric helps judge whether the result is useful. They can differ.

| Task | Output | Common training loss | Example |
|---|---|---|---|
| Binary classification | one of two labels | binary cross-entropy | fraud or not fraud |
| Multi-class classification | one of several labels | cross-entropy | which dog breed |
| Multi-label classification | any subset of labels | binary cross-entropy per label | tags for a photo |
| Regression | a number | mean squared or absolute error | house price |
| Ordinal prediction | an ordered grade | depends on the cost of errors | one-to-five star rating |
| Ranking | an ordering | pairwise or listwise loss | search results |
| Generation | a sequence | often cross-entropy per token | translation or text |

Multi-class and multi-label tasks need different outputs. “Which breed is this dog?” usually has one answer, so the class probabilities compete. “Which tags apply to this photo?” can have several answers at once. Forcing those labels to compete would misrepresent the task. A common choice is one sigmoid output per label.

Ordinal targets have order. Predicting a one-star review as five stars is usually worse than predicting it as four stars. A standard classifier treats both as errors, so choose a method and metric that reflect the cost of the mistake.

## Question 3: features and targets

A supervised dataset often starts as a table. You choose a target column, and the remaining usable columns become features.

```python run setup
import numpy as np, pandas as pd

df = pd.DataFrame({
    "sqm":        [45, 62, 80, 55, 120, 95, 38, 70],
    "bedrooms":   [1, 2, 3, 2, 4, 3, 1, 2],
    "district":   ["c", "n", "n", "c", "s", "s", "c", "n"],
    "price_eur":  [220, 310, 395, 265, 610, 470, 190, 340],
})
df
```

- **Features**, often written as X, are the information available to the model.
- **Target**, often written as y, is the answer the model should predict.
- A **sample** is one row. It is also called an example or observation.

In the example, X has eight rows and two columns; y has eight values. Shape matters: X should usually keep a feature dimension, even when it has one column. The target is usually a one-dimensional array.

```python run
X = df[["sqm", "bedrooms"]].values      # numeric features only, for now
y = df["price_eur"].values
X.shape, y.shape
```

### Represent categories

A column such as district contains names. Models need a numerical representation, but assigning arbitrary numbers can create a false order. Mapping centre, north, and south to 0, 1, and 2 implies that the values have a meaningful distance and order.

One-hot encoding makes a separate column for each category:

```python run title="one-hot: k categories become k columns"
onehot = pd.get_dummies(df["district"], prefix="d", dtype=int)
pd.concat([df[["sqm"]], onehot], axis=1).head(4)
```

Each row has a 1 in the column for its category and 0s elsewhere. This avoids inventing an order. The trade-off is size: a column with many distinct values can create many new features. Embeddings provide a compact learned representation for high-cardinality categories; Chapter 12 introduces them.

### Watch for leakage

Leakage occurs when a feature contains information that would not be available when the model makes its prediction. It can produce excellent test scores and poor real-world results.

```python run title="a 100%-accurate model that is worthless"
from sklearn.linear_model import LinearRegression

leaky = df.copy()
leaky["price_per_sqm"] = leaky["price_eur"] / leaky["sqm"]   # <- uses the target

Xl = leaky[["sqm", "price_per_sqm"]].values
model = LinearRegression().fit(Xl, y)
print(f"R^2 = {model.score(Xl, y):.4f}   (suspiciously perfect)")
```

Here, price per square metre was calculated using the price the model is meant to predict. The feature gives away the answer. Similar problems can be harder to spot:

- A timestamp may be written only after a case is resolved.
- An ID may reveal which hospital or region handled a case.
- A status field may be updated after the outcome.
- Duplicate records may appear in both training and validation data.

For each feature, ask: “Would this value exist at the moment the prediction is needed?” Use only information that is available by that point. When results are much better than expected, inspect the data and the split before celebrating.

## Inspect the dataset

Before training, check the column types, missing values, target balance, and relationships between features and target. Plot the data when possible.

```python run title="1. what is even here"
print(df.dtypes.to_dict()); print()
print(df.describe().round(1))
```

A majority-class baseline shows how well a trivial rule performs. If 95% of examples belong to one class, a model that always predicts that class already gets 95% accuracy.

```python run title="2. how balanced is the target"
import numpy as np
labels = np.array([0]*950 + [1]*50)          # a realistic fraud-ish target
print("class balance:", np.bincount(labels))
print(f"always-predict-0 accuracy: {(labels == 0).mean():.1%}")
```

That score may still be useless if the minority class is the one you need to find. Report class balance and choose metrics that reflect the errors that matter. Chapter 16 covers this in detail.

Next, check whether the features contain a signal related to the target:

```python run title="3. does any feature move the target"
print(df.groupby("district")["price_eur"].agg(["mean", "count"]))
```

Then plot the values. A summary statistic can hide patterns, curves, and outliers:

```python run title="4. look at it"
import matplotlib.pyplot as plt
plt.figure(figsize=(5, 3))
plt.scatter(df["sqm"], df["price_eur"])
plt.xlabel("sqm"); plt.ylabel("price (k EUR)"); plt.title("always plot it")
plt.tight_layout()
```

Anscombe's quartet is a classic demonstration: four small datasets share similar summary statistics but look very different when plotted. Visual checks can reveal structure that averages and correlations miss.

## Decide whether machine learning fits

Work through these questions before training:

1. **Does the available data contain evidence for the decision?** A model cannot recover information that was never recorded. Human judgement can be a useful first check, though models can also find patterns that are difficult for people to see.
2. **Do you have enough relevant examples?** Count examples of the outcome you care about, especially rare positive cases. A million records with eleven fraud cases still provides only eleven fraud examples. The amount needed depends on the task, data quality, and whether you can start from a pretrained model.
3. **Will future data resemble the training data?** Changes in users, prices, policies, or collection methods can make old patterns less useful. This is distribution shift. Plan to monitor performance after deployment.
4. **What is the cost of each kind of mistake?** Write down the costs of false positives and false negatives in terms your team understands. Those costs affect the metric and decision threshold.

Compare with a simple baseline before adding complexity. Depending on the task, predict the mean, predict the majority class, use a fixed rule, or carry forward the latest value. Later models need to improve on that reference by enough to justify their cost.

## Practice: frame three tasks

For each task, identify the feedback, output, features, target, one possible leakage source, and a simple baseline. Then decide whether machine learning is appropriate.

1. Predict which users will cancel next month.
2. Find support tickets that describe the same underlying bug.
3. Calculate tax owed on an invoice.

**Predicting cancellations** is a supervised classification task. Possible features include usage, tenure, support contacts, plan, and payment history. The target is whether the user cancels in the following month. Use a fixed cutoff date and include only information available before it. A simple baseline might flag users with no logins in the last 30 days. Accuracy may be a poor metric because the cost of missing a cancellation can differ from the cost of offering a discount unnecessarily.

**Finding related tickets** can be framed as retrieval: represent each ticket and return the closest matches for a person to review. Check for pairs that support staff have already linked; these provide useful labels. A simple text-similarity method is a practical baseline.

**Calculating tax** is usually a rules-based task because the amounts and rates are specified. Implement the arithmetic directly. If the input is a scanned invoice, extracting line items from the image may require machine learning; the tax calculation can still use explicit rules.

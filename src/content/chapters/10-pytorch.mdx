You've now written a forward pass, a backward pass and a training loop with
nothing but NumPy. Today we throw almost all of it away.

And I want to be clear about why that was still worth doing. The point of the
last two days wasn't to build a library — it was so that you know *exactly what
you're throwing away*. Because that is precisely what you'll be debugging for the
rest of your career, and it will be invisible.

## Tensors are arrays with two extra fields

```python run local title="familiar, with additions"
import torch
import numpy as np

t = torch.arange(6.).reshape(2, 3)
print(t)
print(f"shape {tuple(t.shape)}  dtype {t.dtype}  device {t.device}  grad {t.requires_grad}")
```

<Py id="torch-tensor">A tensor</Py> is a NumPy array plus two things: **a device**
(where the memory lives) and **a place on the autograd tape** (how this value was
computed).

That's the entire conceptual addition. Everything else you already know:
<Py id="broadcasting">broadcasting</Py>, <Py id="axis">axes</Py>,
<Py id="matmul">`@`</Py>, <Py id="reshape">reshape</Py>. Chapter 2 was not wasted.

```python run local title="the vocabulary differs slightly"
a = torch.randn(4, 5)
print("numpy  a.reshape(-1)   ->  torch  a.view(-1)   ", tuple(a.view(-1).shape))
print("numpy  a.sum(axis=0)   ->  torch  a.sum(dim=0) ", tuple(a.sum(dim=0).shape))
print("numpy  np.concatenate  ->  torch  torch.cat    ", tuple(torch.cat([a, a]).shape))
print("shares memory with numpy:", np.shares_memory(a.numpy(), a.numpy()))
```

`axis` becomes `dim`. `reshape` also exists as `view` (which needs contiguous
memory and is free). And the default float type is **`float32`, not `float64`**.

That last one catches absolutely everybody. `torch.tensor([1, 2, 3])` gives you
an *integer* tensor, which then explodes somewhere completely unhelpful three
function calls later.

<Aside type="rust">
`.numpy()` and `torch.from_numpy()` **share the buffer** rather than copying. The
two objects are different views of the same allocation, and mutating one mutates
the other.

It's the same aliasing hazard as a NumPy slice, and the same total absence of a
compiler to warn you about it. You know the shape of this bug already; now you
know it lives here too.
</Aside>

## Autograd replaces your backward pass

```python run local title="the tape"
x = torch.tensor(3.0, requires_grad=True)
y = x ** 2 + 5 * x
y.backward()
print(f"y = x^2 + 5x  at x=3  ->  dy/dx = {x.grad.item()}   (analytically 2*3 + 5 = 11)")
```

Notice what did *not* happen there: nothing did algebra.

PyTorch didn't differentiate $x^2 + 5x$ symbolically. It recorded that a squaring
and a multiplication happened, and then <Py id="autograd">`.backward()`</Py>
walked that record in reverse, applying local derivatives one at a time.

That's your bucket brigade from yesterday, generated automatically.

```python run local title="your network's gradients, checked against yesterday's"
torch.manual_seed(0)
X = torch.randn(50, 2)
y = (X[:, 0] * X[:, 1] > 0).float()

W1 = torch.randn(2, 8, requires_grad=True)
b1 = torch.zeros(8, requires_grad=True)
W2 = torch.randn(8, 1, requires_grad=True)
b2 = torch.zeros(1, requires_grad=True)

a1 = torch.relu(X @ W1 + b1)
p  = torch.sigmoid(a1 @ W2 + b2).squeeze()
loss = torch.nn.functional.binary_cross_entropy(p, y)
loss.backward()

# The same expression you derived in step 2 of chapter 9:
manual_gW2 = a1.T @ ((p - y).unsqueeze(1) / len(y))
print("autograd matches the hand derivation:",
      torch.allclose(W2.grad, manual_gW2, atol=1e-6))
```

`True`.

That's the whole of chapter 9, verified against the library. The expression you
derived on paper — `a1.T @ (prediction - target) / n` — is exactly what PyTorch
computes. It just does it for arbitrary graphs, without anybody writing it down.

<Aside type="key">
The real gift here is *not brevity*.

It's that autograd is correct for **any** graph you build — including one you
invent this afternoon that nobody has ever written down.

Your hand-written backward pass is correct for exactly the architecture you
derived it for. Change a layer and you rederive it, and re-gradient-check it, and
find the transpose you got wrong. Autograd just... keeps being right.
</Aside>

## `nn.Module`

```python run local setup title="the same network, declared"
import torch.nn as nn

class Net(nn.Module):
    def __init__(self, n_in=2, hidden=32, n_out=1):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(n_in, hidden),
            nn.ReLU(),
            nn.Linear(hidden, n_out),
        )
    def forward(self, x):
        return self.net(x)          # logits, not probabilities — see below

model = Net()
print(model)
print("parameters:", sum(p.numel() for p in model.parameters()))
```

<Py id="nn-module">`nn.Module`</Py> discovers its parameters by walking the
attributes you assign to `self`. A bit of Python magic, and a genuinely good idea:
it's how `model.parameters()` enumerates every weight in a network of arbitrary
depth without you maintaining a list, and how `model.to(device)` moves all of
them at once.

`nn.Linear(a, b)` holds a weight of shape `(b, a)` and a bias of shape `(b,)`,
and computes `x @ W.T + b`. Same arithmetic as chapter 8, transposed by
convention. (Yes, that convention will trip you up once. Everyone.)

<Aside type="warn">
Notice `forward` returns **logits** — raw scores — not probabilities. That's not
sloppiness on my part. It's required.

`nn.BCEWithLogitsLoss` and `nn.CrossEntropyLoss` apply the sigmoid or softmax
*internally*, using a numerically stable formulation that never computes
`exp(something large)`.

If you apply the sigmoid yourself and then use `BCELoss`, you get the same answer
on easy data — and `nan` on hard data. Which is the worst possible failure mode:
it works in testing and breaks in production.

The rule: **your model outputs logits; the loss function owns the squashing.**
Apply sigmoid or softmax only at inference, when you genuinely want a probability
to show somebody.
</Aside>

## The training loop

```python run local setup title="every PyTorch script you will ever read"
from sklearn.datasets import make_moons
from sklearn.model_selection import train_test_split

Xn, yn = make_moons(n_samples=2000, noise=0.22, random_state=0)
Xn = (Xn - Xn.mean(0)) / Xn.std(0)
Xtr, Xva, ytr, yva = train_test_split(Xn, yn, test_size=0.25, random_state=0, stratify=yn)

Xtr = torch.tensor(Xtr, dtype=torch.float32); ytr = torch.tensor(ytr, dtype=torch.float32)
Xva = torch.tensor(Xva, dtype=torch.float32); yva = torch.tensor(yva, dtype=torch.float32)

torch.manual_seed(0)
model = Net()
loss_fn = nn.BCEWithLogitsLoss()
opt = torch.optim.AdamW(model.parameters(), lr=1e-2)

for epoch in range(300):
    model.train()
    opt.zero_grad()                       # 1. clear last step's gradients
    logits = model(Xtr).squeeze()         # 2. forward
    loss = loss_fn(logits, ytr)           # 3. score
    loss.backward()                       # 4. backward
    opt.step()                            # 5. update

    if epoch % 100 == 99:
        model.eval()
        with torch.no_grad():
            acc = ((model(Xva).squeeze() > 0).float() == yva).float().mean()
        print(f"epoch {epoch+1:3d}   loss {loss.item():.4f}   valid acc {acc:.3f}")
```

Look at the five numbered lines.

**Those five lines are the whole of deep learning.** Every training script you
will ever read — a two-layer toy, a vision model, somebody's frontier language
model — is that sequence, plus logging, plus a data loader.

Zero, forward, score, backward, step. When you open an unfamiliar repository,
find those five lines first. Everything else is scaffolding around them.

<Aside type="warn">
`opt.zero_grad()` is not optional, and forgetting it does not error.

PyTorch **accumulates** into `.grad` rather than overwriting, because that lets
you split one large batch across several backward passes — a genuinely useful
feature that costs you this footgun.

Without `zero_grad()`, step 50 uses the sum of the first fifty gradients. The
effective learning rate grows without bound. Training diverges. No message, no
warning, no clue.

It is the most common PyTorch bug in existence, and you'll produce it deliberately
in the exercises so you recognise the shape of it forever.
</Aside>

`model.train()` and `model.eval()` toggle a flag that changes the behaviour of
dropout and batch normalisation — dropout is off at evaluation, and batch norm
uses running statistics instead of batch statistics. On *this* network they do
absolutely nothing, and building the habit now costs you nothing either.

<Py id="with-statement">`with torch.no_grad()`</Py> stops building the tape,
saving memory and time when you're not going to call `.backward()`.

## Data loading

```python run local title="Dataset and DataLoader"
from torch.utils.data import TensorDataset, DataLoader

train_dl = DataLoader(TensorDataset(Xtr, ytr), batch_size=64, shuffle=True)

torch.manual_seed(0)
model = Net()
opt = torch.optim.AdamW(model.parameters(), lr=1e-2)

for epoch in range(20):
    model.train()
    for xb, yb in train_dl:                      # <- the only change
        opt.zero_grad()
        loss_fn(model(xb).squeeze(), yb).backward()
        opt.step()

model.eval()
with torch.no_grad():
    acc = ((model(Xva).squeeze() > 0).float() == yva).float().mean()
print(f"mini-batch training, valid acc {acc:.3f}")
```

One extra `for` line, and you have the mini-batching you hand-rolled in chapter 5.

<Py id="dataloader">`Dataset`</Py> answers exactly two questions: "how many?" and
"give me item *i*". `DataLoader` turns that into shuffled, batched, optionally
parallel-prefetched tensors.

The separation is the good idea, and it's worth admiring for a second: `Dataset`
knows your file format and nothing whatsoever about batching. `DataLoader` knows
about batching and nothing whatsoever about your files. Two small interfaces that
compose, instead of one big one that does everything.

## Devices, and Apple Silicon

```python run local title="pick the device once"
def best_device():
    if torch.cuda.is_available():
        return torch.device("cuda")
    if torch.backends.mps.is_available():
        return torch.device("mps")          # Apple Silicon GPU
    return torch.device("cpu")

dev = best_device()
print("using:", dev)

m = Net().to(dev)
x = torch.randn(256, 2, device=dev)
print("forward on device:", tuple(m(x).shape), m(x).device)
```

Two tensors on different devices cannot be combined, and mercifully the error
says so in plain English. The idiom is to choose the device once at the top of
your script and route everything through that one variable.

<Aside type="nice">
**MPS** is Apple's Metal backend, and on an Apple Silicon Mac it's a real speedup
over CPU for anything convolutional.

Two caveats worth knowing. Some operations are still unimplemented and fall back
to CPU — set `PYTORCH_ENABLE_MPS_FALLBACK=1` so that happens silently instead of
raising. And `float64` isn't supported on MPS at all, which is one more reason
everything in this world is `float32`.

Here's the fun part, though: for a network this small, **MPS is slower than
CPU**. Kernel-launch overhead dominates when there's barely any arithmetic to do,
and you spend more time talking to the GPU than the GPU spends working.

Device choice is worth measuring, not assuming. "Use the GPU" is not a law.
</Aside>

## What the library actually gave you

```python run local title="the honest accounting"
print("NumPy version (chapter 9): ~24 lines of init + forward + backward + loop")

    "a data pipeline with parallel prefetch",

    print(" *", item)
```

The line count is the least interesting item on that list.

The first one is what matters. The moment you want a residual connection, or a
custom loss, or an architecture you read about this morning on arXiv, the
hand-written version needs a fresh derivation and a fresh gradient check and an
afternoon.

Autograd needs nothing. You just write the forward pass and the gradients come
for free, correct, first time.

<Aside type="key">
Which is exactly why the two days deriving it by hand were worth spending.

When your loss goes to `nan`. When a gradient is silently zero. When a layer
stubbornly refuses to learn. You now know what's happening underneath — and that
is the entire difference between debugging and guessing.

People who skip chapters 8 and 9 don't write worse code. They write the same
code, and then they can't fix it.

## The bugs you will hit

```python run local title="the five-minute reference"
# 1. integer tensor where a float was expected
try:
    nn.Linear(3, 1)(torch.tensor([[1, 2, 3]]))
except Exception as e:
    print("1.", type(e).__name__, "->", str(e)[:88])

# 2. calling backward twice on the same graph
z = torch.tensor(2.0, requires_grad=True) ** 2
z.backward()
try:
    z.backward()
except Exception as e:
    print("2.", type(e).__name__, "->", str(e)[:88])

# 3. the silent one: a shape mismatch that broadcasts instead of failing
pred = torch.randn(8, 1)      # model output
targ = torch.randn(8)         # labels
print("3. (pred - targ).shape =", tuple((pred - targ).shape), "  <- should be (8,), got 8x8")
```

1. **dtype.** `torch.tensor([1, 2, 3])` is `int64`. Write `1.` or pass `dtype=`.
2. **Freed graph.** The tape is discarded after `backward()`. If you find yourself
   wanting `retain_graph=True`, you almost always meant to accumulate the loss and
   call backward once.
3. **Shape.** This is the dangerous one, because it *does not raise*. `model(x)`
   gives `(n, 1)`, your labels are `(n,)`, so the subtraction
   <Py id="broadcasting">broadcasts</Py> into `(n, n)` — and your loss is now the
   mean of 64 completely meaningless numbers, which trains to something, slowly,
   wrongly.

   `.squeeze()` the output or `.unsqueeze(1)` the labels. And print both shapes
   the instant a loss looks strange.

Two more with no error message at all: **forgetting `zero_grad()`** (divergence,
no signal) and **forgetting `model.eval()`** (validation scores mysteriously
worse than training, because dropout is still on).

**"`RuntimeError: expected scalar type Long but found Float`"** — that's bug 1.

**"My loss is a tensor, not a number."** It is! `loss.item()` pulls the Python
float out. Printing the tensor directly also shows `grad_fn=<...>`, which is the

**"Why `.squeeze()` everywhere?"** Because `nn.Linear(h, 1)` outputs `(n, 1)` and

squeeze consistently.

forgot to reassign — `model.to(dev)` returns the model for modules, but tensors
need `x = x.to(dev)`.

<Fragment slot="answer">

```python run local
# 3. Life without zero_grad
torch.manual_seed(0)
m = Net(); o = torch.optim.SGD(m.parameters(), lr=0.01)
for epoch in range(6):
    # o.zero_grad()   <- deliberately missing
    loss = loss_fn(m(Xtr).squeeze(), ytr)
    loss.backward()
    norm = sum(p.grad.norm().item() ** 2 for p in m.parameters()) ** 0.5
    o.step()
    print(f"epoch {epoch}  loss {loss.item():.4f}  grad norm {norm:8.3f}")
```

The gradient norm climbs every single epoch, because each `backward()` *adds* to
what was already sitting there.

By epoch 6 the effective learning rate is several times what you asked for, and
it keeps growing. On a real run this reaches `inf`, then `nan` — with no error, no
warning, and no clue as to why.

Now you've seen the shape of it: **loss diverging and gradient norm climbing
monotonically**. That pattern means `zero_grad()`, essentially always.

```python run local
# 4. Dropout behaves differently in train() and eval()
class Dropped(nn.Module):
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(2, 32), nn.ReLU(),
                                 nn.Dropout(0.3), nn.Linear(32, 1))
    def forward(self, x): return self.net(x)

torch.manual_seed(0)
d = Dropped(); o = torch.optim.AdamW(d.parameters(), lr=1e-2)
for _ in range(300):
    d.train(); o.zero_grad()
    loss_fn(d(Xtr).squeeze(), ytr).backward(); o.step()

d.train()
with torch.no_grad():
    a = [round((((d(Xva).squeeze() > 0).float() == yva).float().mean()).item(), 4) for _ in range(3)]
d.eval()
with torch.no_grad():
    b = round((((d(Xva).squeeze() > 0).float() == yva).float().mean()).item(), 4)
print("train() mode, three runs:", a, " <- different each time")
print("eval()  mode:            ", b, " <- deterministic")
```

Three runs, three different answers — from the *same model* on the *same data*.

In `train()` mode, dropout randomly zeroes 30% of the hidden units on every
forward pass, so the same input genuinely gives a different answer each time. In
`eval()` mode dropout becomes a no-op and every unit contributes.

And that randomness is the entire point of dropout. It forces the network not to
depend on any single unit, because that unit might not be there. It's
[regularisation](/learn/06-generalisation/) by deliberate sabotage — you damage
the model during training so it learns to be robust, and then you stop damaging
it.

Which is also, incidentally, why forgetting `model.eval()` produces validation
numbers that are inexplicably worse than they should be. You left the sabotage
running.

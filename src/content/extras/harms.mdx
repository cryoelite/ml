Machine learning systems can repeat patterns in their data, fail more often for some groups, or change the world they measure. These risks matter most when a model affects people’s access to money, work, care, safety, or information.

## Historical data can carry unfair decisions

A model learns patterns from examples. If the examples reflect unequal treatment, the model may learn to repeat it.

For example, past hiring decisions may reflect who a company preferred, rather than who could do the job. Arrest records reflect where police looked, not only where crime happened. Health spending can look like a measure of need, but it also reflects who had access to care. If a model is trained to predict spending, it may mistake lower access for lower need.

Removing a sensitive column does not guarantee fair results. Other inputs can carry similar information. A location, name, or purchase history may reveal patterns linked to a protected group. Keep the information needed to check outcomes, and measure performance across groups.

## Feedback can reinforce a model’s predictions

Suppose a system sends more patrols to places with more recorded crime. More patrols can lead to more recorded incidents. The next model then sees those records and sends more patrols there again.

Similar loops can occur in recommendations, credit, and hiring. A recommendation gets more attention because it is shown more often. A person denied credit may have fewer chances to build a repayment history.

When possible, keep a way to observe outcomes outside the model’s decisions. That helps you tell whether the model is measuring a real pattern or reinforcing its own earlier choices.

## Overall scores can hide who is struggling

This example gives a model high overall accuracy, even though it makes many more mistakes for one group.

```python run title="93% accurate, and failing one user in ten"
import numpy as np
rng = np.random.default_rng(0)

n_major, n_minor = 9000, 1000
correct = np.concatenate([
    rng.random(n_major) < 0.96,      # the majority group
    rng.random(n_minor) < 0.68,      # a group with far less training data
])
group = np.array(["majority"] * n_major + ["minority"] * n_minor)

print(f"overall accuracy      : {correct.mean():.1%}")
for g in ["majority", "minority"]:
    m = group == g
    print(f"  {g:9s} ({m.sum():5,d}) : {correct[m].mean():.1%}")
print("\nThe headline number is fine. One in ten users gets a system that")
print("fails nearly a third of the time, and no aggregate metric shows it.")
```

Check important metrics by relevant groups, as well as overall. A single average cannot tell you whether the system works equally well for everyone.

A 2018 study of three commercial gender-classification systems reported error rates up to 34.7% for darker-skinned women and 0.8% for lighter-skinned men in its evaluation. The result showed why the makeup of an evaluation set matters. [Read the study](https://proceedings.mlr.press/v81/buolamwini18a.html).

## Fairness has more than one definition

Fairness measures can ask different questions. Demographic parity compares the rate of positive decisions. Equal opportunity compares true-positive rates. Predictive parity compares precision.

When groups have different underlying rates and predictions are imperfect, some combinations of these measures cannot all hold at once. The right choice depends on the decision and its consequences. Make the choice explicit, explain why it fits, and involve the people accountable for the system. [Kleinberg, Mullainathan, and Raghavan describe this trade-off](https://arxiv.org/abs/1609.05807).

This example uses the same score rule for two groups with different base rates.

```python run title="you have to choose, and the choice has consequences"
# Two groups, different base rates, one shared threshold.
rng = np.random.default_rng(1)
def group_stats(n, base_rate, sep=1.1):
    y = (rng.random(n) < base_rate).astype(int)
    s = np.where(y == 1, rng.normal(sep, 1, n), rng.normal(0, 1, n))
    return y, s

for name, base in [("group A", 0.30), ("group B", 0.10)]:
    y, s = group_stats(4000, base)
    pred = (s > 1.0).astype(int)
    tp = ((pred == 1) & (y == 1)).sum(); fp = ((pred == 1) & (y == 0)).sum()
    fn = ((pred == 0) & (y == 1)).sum()
    print(f"{name}: base rate {y.mean():.0%}   flagged {pred.mean():.1%}   "
          f"precision {tp/max(tp+fp,1):.2f}   recall {tp/max(tp+fn,1):.2f}")
print("\nSame model, same threshold. The rates differ because the base rates do.")
print("Equalising any one column requires unequalising another.")
```

## Fluent output can still be wrong

Language models can produce smooth, confident text without checking whether it is true. A fabricated source or incorrect summary can cause harm when a user cannot verify it.

For tasks where accuracy matters, make sources easy to check, use code for calculations, and show uncertainty when it is relevant. Design the experience so a person can make an informed decision instead of quickly approving a model’s suggestion.

## Data work has human costs

Training data may include people’s writing, images, records, or code. Ask how it was collected and whether the people involved knew how it would be used. Annotation and content review can also involve low-paid or stressful work. Those costs belong in an honest account of a system.

## Practical checks

1. Compare key metrics across groups before reporting one overall result.
2. Record the model’s intended use, training data, evaluation results, and known limits.
3. Ask who created the labels and what those labels actually measure.
4. For consequential decisions, give people a meaningful way to review and change outcomes.
5. Keep enough logs to investigate errors, including the model version.
6. Say when the evidence is too limited to know whether the system works for a group.

The core question is not only “How often is the model right?” Ask who it is wrong for, and what happens when it is wrong.

A useful model must fit the time and memory limits of the system that runs it. Measure the full prediction path first. Then choose an optimisation that targets the measured bottleneck.

## Measure latency and memory

Latency varies from request to request. Look at percentiles, not only the average.

```python run setup title="latency is a distribution, not a number"
import numpy as np
rng = np.random.default_rng(0)

# A realistic latency profile: mostly fast, with a tail.
latencies = np.concatenate([
    rng.gamma(4, 6, 9500),          # the common case
    rng.gamma(4, 40, 500),          # cache misses, GC pauses, cold starts
])

print(f"mean    {latencies.mean():7.1f} ms")
for q in [50, 90, 95, 99, 99.9]:
    print(f"p{q:<5}  {np.percentile(latencies, q):7.1f} ms")
print(f"max     {latencies.max():7.1f} ms")
```

Measure the whole path: data lookup, preprocessing, model execution, and output handling. If the model takes only a small part of the total time, making it faster will have a limited effect.

## Batching: improve throughput

Batching lets hardware process several requests together. This can improve throughput, but each request may wait longer before it is processed.

```python run title="throughput against batch size"
# Cost model: a fixed per-call overhead plus work proportional to the batch.
OVERHEAD_MS, PER_ITEM_MS = 8.0, 0.35

print(f"{'batch':>6s} {'latency':>10s} {'throughput':>14s} {'per item':>11s}")
for b in [1, 4, 16, 64, 256]:
    latency = OVERHEAD_MS + PER_ITEM_MS * b
    print(f"{b:6d} {latency:8.1f} ms {b / latency * 1000:11.0f}/s "
          f"{latency / b:9.2f} ms")
```

Servers often use dynamic batching: wait briefly to collect requests, then run them together. Choose the wait time based on the latency and throughput needs of the application.

## Quantisation: store weights with fewer bits

Quantisation uses lower-precision numbers to reduce model memory and sometimes improve speed.

```python run title="what precision actually costs"
n_params = 7_000_000_000
print(f"{'precision':>12s} {'bits':>6s} {'7B model':>12s} {'fits on':>28s}")
for name, bits, note in [
    ("float32", 32, "an 80 GB A100, barely"),
    ("float16",  16, "a 40 GB card"),
    ("int8",      8, "a 16 GB card"),
    ("int4",      4, "a 12 GB consumer GPU"),
]:
    gb = n_params * bits / 8 / 1e9
    print(f"{name:>12s} {bits:6d} {gb:10.1f} GB {note:>28s}")
```

This simple example measures how rounding changes weights. Weight similarity is not the same as model accuracy, so evaluate the quantised model on the real task.

```python run title="what you lose, measured"
rng = np.random.default_rng(1)
w = rng.normal(0, 0.4, 100_000).astype(np.float32)

def quantise(x, bits):
    """Symmetric linear quantisation: scale to the integer range, round, scale back."""
    qmax = 2 ** (bits - 1) - 1
    scale = np.abs(x).max() / qmax
    return np.round(x / scale).clip(-qmax - 1, qmax) * scale

print(f"{'bits':>5s} {'mean abs error':>16s} {'relative':>10s} {'correlation':>13s}")
for bits in [16, 8, 4, 2]:
    q = quantise(w, bits)
    err = np.abs(q - w).mean()
    print(f"{bits:5d} {err:16.6f} {err / np.abs(w).mean():9.2%} "
          f"{np.corrcoef(w, q)[0, 1]:13.6f}")
```

Per-channel or per-group scales can represent different ranges more efficiently. Quantisation-aware training simulates rounding during training and can help when post-training quantisation causes too much quality loss.

## Distillation: train a smaller model from a larger one

A student model can learn from a teacher’s probability distribution as well as from hard labels.

```python run title="why soft targets teach more than hard ones"
teacher_logits = np.array([4.0, 2.5, 2.2, -1.0, -3.0])
classes = ["cat", "lynx", "tiger", "car", "spanner"]

def softmax(z, T=1.0):
    z = np.asarray(z) / T; z = z - z.max(); e = np.exp(z); return e / e.sum()

print(f"{'class':>9s} {'hard label':>11s} {'T=1':>8s} {'T=3':>8s}")
for i, c in enumerate(classes):
    print(f"{c:>9s} {1.0 if i == 0 else 0.0:11.1f} "
          f"{softmax(teacher_logits)[i]:8.3f} {softmax(teacher_logits, 3)[i]:8.3f}")
```

Soft targets can show which alternatives the teacher considers similar. Their usefulness depends on the task and the teacher’s quality. Distillation still needs evaluation against the original model and the intended use.

## Caching repeated work

Language models can reuse keys and values from earlier tokens during generation. This avoids recomputing them at each step, at the cost of memory that grows with sequence length and batch size.

```python run title="a KV cache changes the complexity class"
def cost_without_cache(n):
    """Regenerating all attention every step: sum of k^2 for k = 1..n."""
    return sum(k ** 2 for k in range(1, n + 1))

def cost_with_cache(n):
    """Keys and values for past tokens are reused: sum of k."""
    return sum(range(1, n + 1))

print(f"{'tokens':>8s} {'no cache':>14s} {'with cache':>13s} {'speedup':>9s}")
for n in [10, 100, 500, 2000]:
    a, b = cost_without_cache(n), cost_with_cache(n)
    print(f"{n:8d} {a:14,d} {b:13,d} {a / b:8.0f}x")
```

Other caches can reuse repeated embeddings, features, or identical requests. Measure how often work repeats and how fresh the cached result must be.

## Other options

- **Pruning:** remove weights or structures that contribute little. Speed gains depend on whether the hardware supports the resulting sparsity.
- **Compilation:** tools such as PyTorch compilation or ONNX Runtime can combine operations and improve execution.
- **Early exit:** use a smaller model for easy examples and a larger one for uncertain cases.
- **Speculative decoding:** let a smaller model draft tokens that a larger model can check in parallel.

These methods involve different trade-offs. Verify current tool support and measure the result on your hardware.

## A sensible order

| Step | What to learn or try |
|---|---|
| 1. Profile the full path | Find the actual bottleneck |
| 2. Cache repeated work | Avoid duplicate computation |
| 3. Batch requests | Improve throughput |
| 4. Compile the model | Reduce execution overhead |
| 5. Try lower precision | Reduce memory and possibly latency |
| 6. Distil or prune | Trade extra work or quality for a smaller model |

Stop when the system meets its requirements. Larger changes such as distillation or pruning need careful accuracy checks; profiling and caching may solve the problem with less work.
